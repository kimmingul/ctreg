# 설계: 선언이 존재가 아니라 내용을 말하게 한다

- **일자:** 2026-08-23
- **다루는 항목:** F2 · F5 · F8 · F9 · F14 (에이전트 필드 테스트 CLI-FIX 우선순위 5번)
- **정본 우선순위:** `docs/agent-field-test-2026-08-22.md` 의 `### CLI-FIX 우선순위`

## 1. 왜 다섯을 함께 고치는가

정본이 이렇게 적어 두었다:

> **F1·F2·F4·F5·F8·F9·F14 는 하나의 패턴이다** — 선언이 불완전하면 에이전트는 한도를
> 부딪혀서만 알게 되고, 부딪힌 것을 알아채지 못하면 조용히 틀린다. 일곱을 따로 고치면
> 패턴은 남아 다음 항목에서 다시 나타난다.

F1·F4 는 이미 닫혔다. 남은 다섯의 뿌리는 하나다 — **`true` 는 축이 있다는 것만 말하고,
그 축이 무엇을 받는지도, 무엇을 보는지도, 데이터를 덮는지도 말하지 않는다.**

각 항목이 그 뿌리의 어느 면인지:

| 항목 | 드러난 방식 | 뿌리의 어느 면 |
| :-- | :-- | :-- |
| **F2** | `term: true` 를 보고 EudraCT 번호로 조회 → 0건. "없음"인지 "안 봄"인지 판별 불가 | 축이 **무엇을 보는지** 안 말한다 |
| **F5** | `--phase` 에 틀린 값을 일부러 넣어 힌트를 캐내고 나머지는 추측 | 축이 **무엇을 받는지** 안 말한다 |
| **F9** | 대문자 값 거부 → 힌트. 세 시나리오가 같은 힌트를 **틀린 뒤에** 받음 | 같음 — 값 어휘를 미리 안 말한다 |
| **F8** | 범주별 건수의 합이 총계에 못 미치는데 모자란 부분에 이름을 붙일 수단이 없음 | 어휘가 **데이터를 덮는지** 안 말한다 |
| **F14** | `results: true` 를 "결과 유무로 검색 가능"으로 오독 | 불리언이 **무엇에 대한 참인지** 안 말한다 |

### 이 작업 중에 새로 생긴 증거

두 번째 어댑터(ISRCTN)가 같은 패턴을 하나 더 만들었다. ISRCTN 의 phase 어휘에는
`early_phase_1` 에 해당하는 값이 없어서, `--phase early_phase_1 --registry isrctn` 은
**exit 2 로 거부된다**(`src/adapters/isrctn/query.ts`). 옳은 동작이지만 —— 조용히 넓히는
것보다 낫다 —— 사용자는 여전히 **부딪혀야만** 안다. 선언에 그 사실이 없다.

레지스트리가 늘수록 이런 구멍도 는다. 지금 고치지 않으면 어댑터 #3 에서 다시 나타난다.

## 2. 설계 원칙

1. **발견 창구는 하나다.** `ctreg registries` 는 이미 "요청을 조립하기 전에 먼저 부르는,
   네트워크를 타지 않는 커맨드"로 설계돼 있다. 새 커맨드를 만들면 에이전트가 둘을 다 알아야
   하고, "어디서 물어보나"가 축마다 달라진다 — F2 가 지적한 것이 바로 그 종류의 불규칙성이다.
2. **선언은 정적이고 무료다.** `registries` 는 네트워크를 타지 않는다. 이 성질을 깨지 않는다.
3. **선언이 참인지는 실물이 판정한다.** ISRCTN 어댑터에서 세운 방식 그대로 —— 선언은
   코드에, 증명은 필드테스트 스크립트에. 선언과 실물이 어긋나면 스크립트가 빨간 줄을 낸다.
4. **값 목록을 손으로 두 번 적지 않는다.** 이미 있는 매핑 테이블에서 파생한다. 두 테이블이
   어긋나는 사고를 막는 기존 설계(`STATUS_OUT` 이 `STATUS_IN` 에서 파생되는 것)를 그대로 잇는다.
5. **새 개념을 만들지 않는다.** F8 의 경고는 이미 있는 `date_filter_excludes_missing` 과
   같은 자리·같은 모양이다. enum 축으로 넓히는 것이지 새 장치가 아니다.

## 3. Capability 스키마 변경

### 3.1 검색 축: 불리언 → `SearchAxis`

```ts
const SearchAxisSchema = z.strictObject({
  supported: z.boolean(),
  /**
   * 이 레지스트리가 **필터로 받을 수 있는** 공통 어휘 값.
   * - 배열  — 닫힌 어휘 축. 여기 없는 값은 exit 3/2 로 거부된다.
   * - null  — 자유 텍스트 축(닫힌 어휘가 없다).
   * 지원하지 않는 축(`supported: false`)은 닫힌 어휘면 `[]`, 자유 텍스트면 `null` 이다.
   */
  values: z.array(z.string()).nullable(),
  /**
   * 이 축의 **필터 가능한 값들이 레지스트리를 남김없이 덮는가.** 닫힌 어휘 축에만
   * 의미가 있고 자유 텍스트 축은 `null`.
   * `false` 면 값별 건수의 합이 전체 총계보다 작다 — 그 차이가 F8 이 이름 붙이지
   * 못했던 부분이다.
   *
   * **원인은 둘이고 이 신고는 둘을 구분하지 않는다:** 그 필드를 기재하지 않은 레코드와,
   * 기재했으나 그 값이 공통 어휘에 **필터 자리가 없는** 레코드다. 후자가 실제로 더 크다 —
   * ctgov 의 status 미달분 97,667건은 전부 후자이고(UNKNOWN 95,620 + 확대접근 1,066 +
   * WITHHELD 981, 산술이 정확히 맞는다), **상태가 없는 레코드는 0건이다.** 사용자에게
   * 중요한 것은 어느 쪽이든 "값별로 세면 총계가 안 맞는다" 는 사실이므로 하나로 신고하되,
   * 경고 문구가 원인을 단정해서는 안 된다.
   *
   * `supported: false` 인 축도 `null` 이다 — 검색할 수 없는 축에 "덮는다/못 덮는다" 는
   * 물음 자체가 성립하지 않는다. 여기에 `true`/`false` 를 적으면 읽는 쪽이 그 축으로
   * 무언가 셀 수 있다고 오해한다.
   */
  exhaustive: z.boolean().nullable(),
  /** 이 축이 실제로 **무엇을 보는지** 한 문장. 불리언이 말하지 못하는 것. */
  scope: z.string().min(1),
});
```

`search` 의 열일곱 축이 전부 이 모양이 된다.

### 3.3 호환성 — 깬다

`search.condition` 이 `true` 에서 객체가 되는 것은 호환을 깨는 변경이다. 깨는 쪽을 택한다:

- 버전은 `0.1.0` 이고 **npm 배포판이 없다**(README 가 소스 빌드를 안내한다).
- 불리언을 읽는 곳은 전부 이 저장소 안이다 — `cli/guard.ts`, 계약 스위트, 테스트.
- **스킬은 안 깨진다.** `skills/ctreg/SKILL.md` 는 의도적으로 얇아 플래그도 필드명도 적지
  않는다(`tests/plugin/skill.test.ts` 가 그 얇음을 고정한다).
- 불리언과 객체를 **나란히** 두는 대안은 같은 사실을 두 곳에 적는 것이고, 이 저장소에서
  그렇게 했다가 한쪽만 갱신된 사고가 이미 두 번 있었다(선결 조건 문서의 F8 추가 기록).

`docs/fieldtest/*.md` 의 옛 출력은 **당시의 기록이므로 고치지 않는다.**

## 4. 값 목록은 레지스트리마다 다르다

이것이 F5 의 실제 답이다. 지금 상태:

| 축 | ctgov | isrctn | 근거 |
| :-- | :-- | :-- | :-- |
| `status` | 8개 전부 | `[]` | ISRCTN 은 `trialStatus`·`recruitmentStatus` 가 실측에서 전부 0건 |
| `phase` | 6개 (`early_phase_1` 포함) | 5개 (**`early_phase_1` 없음**) | API 문서 3.2.1.12 의 값 목록에 자리가 없다 |
| `studyType` | 3개 | 2개 (`expanded_access` 없음) | `primaryStudyDesign` 은 Interventional/Observational 뿐 |

### 파생 방법 — 손으로 적지 않는다

각 어댑터가 이미 "필터로 쓸 수 있는 값"의 정본 테이블을 갖고 있다:

- `src/adapters/ctgov/vocab.ts` 의 `STATUS_OUT` · `PHASE_OUT` · `STUDY_TYPE_OUT`
  (모두 `*_IN` 에서 `isFilterable*` 로 걸러 파생된다 — `unknown`/`other` 는 매핑 결과이지
  필터 입력이 아니므로 자동으로 빠진다)
- `src/adapters/isrctn/query.ts` 의 `PHASE_OUT` · `STUDY_TYPE_OUT`

이 테이블들을 `export` 하고 capability 선언이 그 키를 읽는다. 값을 새로 적지 않으므로,
어휘 테이블과 선언이 어긋날 수 없다.

> **ISRCTN 의 `PHASE_OUT` 은 `query.ts` 에 있고 `vocab.ts` 에 있는 WHO 포맷 매핑과
> 별개다.** 이 분리는 의도된 것이다(query.ts 의 주석 참고) — 하나는 질의로 **나가는**
> 값, 다른 하나는 응답으로 **들어오는** 값이고, 지금 문자열이 같은 것은 우연이다.
> capability 의 `values` 는 **나가는** 쪽에서 파생한다.

## 5. F8 — `exhaustive` 는 실측이다

### 판정 방법

에이전트가 손으로 했던 뺄셈을 그대로 쓴다:

```
값별 건수의 합  vs  같은 질의의 전체 총계
합 < 총계  →  exhaustive: false
```

축 하나당 (값 개수 + 1) 번의 count 요청이면 된다. `count` 는 두 레지스트리 모두 지원하고
ISRCTN 은 `limit=0` 으로 80바이트다.

### 어디서 재는가

필드테스트 스크립트다. `scripts/isrctn-field-test.ts` 에 이미 만든 구조를 따르고,
ctgov 쪽에도 같은 절을 만든다. **선언은 코드에, 증명은 스크립트에** — ISRCTN 어댑터에서
세운 규율 그대로다.

스크립트가 선언과 실측이 어긋나면 실패한다. 즉 `exhaustive` 를 낙관적으로 `true` 로
적어 두면 CI 가 잡는다.

> **구현하며 바뀐 것 (2026-08-23, 최종 리뷰 H1·H2·H3).** 위 뺄셈은 `false` 를 결론짓는
> 데에만 안전하다. 반대 방향(`합 >= 총계` → `true`)은 두 가정에 기대는데 둘 다 항상
> 참은 아니다 — (1) 총계가 정확할 것: ISRCTN 의 기준선은 `lastEdited` 로 잰 **하한**
> 이라 낮춰 잡히면 덮개가 부풀려진다, (2) 축이 분할일 것: ctgov 의 phase 는 한 시험이
> 여러 값에 걸려 합에 중복이 있다. 그래서 실측 판정은 세 값이다 — `false`(합 < 총계),
> `true`(분할 축 · 정확한 총계에서만), **판정 불가**. 증명되지 않은 `true` 신고는 실패이고
> 좁게 신고한 `false` 는 불확정이다. 규칙은 `scripts/exhaustive.ts` 에 있고 두 스크립트가
> 공유한다. 그리고 이 절이 약속한 대조 자체가 처음 구현에는 없었다 — 합을 표에 찍고
> 멈췄다(커밋 `542c16b`).

### 사용 시점의 경고

`exhaustive: false` 인 축으로 필터하면:

```jsonc
{ "code": "vocab_excludes_missing",
  "message": "ctgov 의 'phase' 는 값별로 나눈 건수의 합이 전체보다 작습니다 — 이 값들 중 어디에도 걸리지 않는 시험이 있습니다(그 필드를 기재하지 않았거나, 기재한 값이 공통 어휘에 없습니다). 이 필터의 결과는 그만큼 좁습니다.",
  "registry": "ctgov" }
```

문구가 **원인을 단정하지 않는 것**이 중요하다. "값을 기재하지 않은 시험이 빠집니다" 라고
쓰면 ctgov 의 status 에 대해 거짓이 된다 — 그 미달분은 전부 값이 **있는** 레코드이고,
다만 그 값(`UNKNOWN` 등)이 공통 어휘의 필터 입력이 아닐 뿐이다.

`date_filter_excludes_missing` 과 같은 자리에서 같은 모양으로 난다. 어느 쪽도 종료 코드를
바꾸지 않는다(경고는 exit 를 바꾸지 않는다는 규칙 그대로).

**어디서 내는가:** 어댑터의 질의 빌더가 아니라 **CLI 가드**(`cli/guard.ts`)다. 어댑터마다
같은 경고를 복제하면 M3(페이지 크기 정책)에서 방금 고친 것과 같은 문제가 된다 — 정책이
어댑터 수만큼 생기고, 어긋나도 오류가 아니라 레지스트리마다 다른 침묵으로 나타난다.
가드는 이미 `cap` 과 `q` 를 둘 다 보고 있고 다섯 커맨드가 전부 부른다.

> `assertSupported` 는 지금 **던지기만** 하고 경고를 내지 않는다. 경고를 돌려주려면
> 반환형이 바뀐다(`void` → `{ warnings: Warning[] }`). 호출 지점은 다섯 커맨드다.

## 6. F9 — `--help` 가 값 어휘를 적는다

지금 `--help` 는 이렇게만 적는다:

```
필터      --status --phase --study-type (반복 가능)
```

대소문자 규칙도 값 목록도 없고, **틀린 값을 넣었을 때만** 힌트로 말한다. 세 축의 닫힌
어휘를 `core/vocab.ts` 에서 파생해 적는다.

역할이 나뉜다:

- **`--help` = 이 CLI 가 받는 값** (레지스트리 무관, 공통 어휘)
- **`registries` = 각 레지스트리가 그 값으로 무엇을 하는가** (지원 여부·덮는 범위)

`--help` 는 공통 어휘 전체를 적고, 특정 레지스트리가 그중 일부만 받는다는 사실은
`registries` 가 말한다. 그래야 두 표면이 같은 것을 두 번 적지 않는다.

## 7. 계약 스위트에 더할 검사

### 7.1 신고한 `values` 는 전부 질의로 조립된다

신고해 놓고 `usageError` 로 거부하는 어댑터를 잡는다. **지금 ISRCTN 이 `early_phase_1`
에서 그러고 있고**, 이 검사가 그 불일치를 구조적으로 막는다.

```
cap.search.phase.values 의 각 값 v 에 대해:
  adapter.search({ phase: [v] }, fetchOpts) 가 던지지 않는다
  그리고 나간 요청이 그 축을 실제로 싣는다
```

### 7.2 `supported: false` 인 닫힌 어휘 축은 `values: []` 다

`supported: false` 인데 `values` 에 뭔가 들어 있으면 두 선언이 모순이다.

### 7.3 `scope` 는 비어 있지 않다

스키마의 `z.string().min(1)` 이 이미 강제하지만, 계약 스위트가 **의미 없는 자리채움**
(축 이름을 그대로 되풀이한 것)까지 잡을 수는 없다. 이건 리뷰의 몫으로 남긴다 —
검사로 만들 수 없는 것을 검사인 척하지 않는다.

| `src/cli/args.ts` | USAGE 에 값 어휘 |
| `tests/contract/adapter-contract.ts` | §7 의 검사들 |
| `scripts/isrctn-field-test.ts` | `exhaustive` 실측 절 추가 |
| `scripts/field-test.ts` | ctgov 쪽 `exhaustive` 실측 절 추가 (이미 ctgov 전용 스크립트다 — 새로 만들지 않는다) |
| `README.md` | `registries` 예시 갱신, 값 어휘 안내 |

## 9. 범위에서 뺀 것

- **실측 건수를 응답에 싣는 것** (`coverage: { withValue, missing }`) — 요청이 늘고,
  레지스트리마다 가능 여부가 갈리며, 값이 시간에 따라 변한다. `exhaustive` 불리언 +
  경고로 "합이 총계보다 작다"는 사실은 전달되고, 정확한 수가 필요하면 사용자가
  `count` 를 축별로 부를 수 있다 — 그게 가능하다는 것을 이제 선언이 말해 준다.
- **`ctreg vocab` 별도 커맨드** — 발견 창구를 둘로 나눈다(설계 원칙 1).
- **`GET /studies/enums` 기반 업스트림 원문 어휘 노출** — 이 CLI 의 계약은 공통 어휘이지
  업스트림 원문 어휘가 아니다. 원문이 필요하면 `--raw` 와 `*Raw` 필드가 이미 있다.
- **F6 · F11 · F13 · F3 · F12** — 정본 우선순위의 6·7번이다. 이 설계에 끌어들이지 않는다.

## 10. 이 설계가 틀렸을 수 있는 지점

- **`scope` 문장을 누가 검증하는가.** 자연어라 테스트가 못 잡는다. 틀린 `scope` 는 틀린
  불리언보다 나쁠 수 있다 — 읽는 쪽이 믿기 때문이다. 완화책은 §7.3 에 적었듯 리뷰뿐이고,
  이것이 이 설계에서 가장 약한 고리다.
- **`exhaustive` 는 시간에 따라 변한다.** 오늘 `false` 인 축이 레지스트리가 데이터를
  채우면 `true` 가 될 수 있다(반대도 마찬가지). 필드테스트가 CI 에서 돌면 잡히지만,
  그 스크립트는 네트워크를 타므로 CI 에 넣을지는 별도 판단이 필요하다.
- **열일곱 축에 `scope` 를 다는 비용.** 두 어댑터 × 17축 = 34개 문장이다. 자리채움으로
  채우면 F2 를 고치는 대신 F2 를 흉내만 내게 된다.
