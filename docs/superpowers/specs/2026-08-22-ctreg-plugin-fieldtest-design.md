# ctreg 얇은 플러그인 + 에이전트 필드 테스트 설계

- **일자:** 2026-08-22
- **상태:** 설계 확정. 구현 계획은 별도 문서.
- **선행:** `docs/superpowers/specs/2026-08-22-ctreg-design.md` (CLI 스펙), 슬라이스 1 완료
- **선택한 방안:** A — 얇은 스킬, CLI 자기설명에 최대한 의존

---

## 1. 테제

> 스킬은 규율만 가르치고 표면은 CLI가 스스로 말한다. 에이전트가 헤매는 지점이 곧 CLI 자기설명의 결함이다.

슬라이스 1은 CLI를 완성했지만 **에이전트가 그것을 몬 적이 한 번도 없다.** CLI 스펙 §8.3의 착수 순서 6번이 요구한 "실제 CT.gov + 실제 에이전트 세션" 중 앞의 절반만 수행됐다(`docs/field-test-2026-08-22.md`). 이 작업이 뒤의 절반이다.

동시에 이것은 플러그인의 첫 증분이다 — 버리는 하네스가 아니라 계속 자랄 물건이다.

### 1.1 왜 얇은가

두꺼운 스킬(표면을 SKILL.md에 복제)은 두 가지로 실패한다. CLI와 드리프트하고, **필드 테스트를 무의미하게 만든다** — 스킬이 답을 다 주면 CLI의 자기설명이 충분한지 알 수 없다.

원 검토 문서(`docs/advancement-review-2026-08-21.md` §11)도 같은 방향이다: 스킬이 잘하는 것은 "랜드스케이프는 count 먼저", "적격은 확정이 아니다" 같은 규율이지 툴 표면의 복제가 아니다.

### 1.2 비목표

- 슬래시 커맨드 — 스킬 하나로 에이전트가 굴러가는지가 질문이고, 커맨드는 답을 흐린다
- 워크플로 테제(환자 매칭 / 랜드스케이프 / 결과 비교) — 기계적 사용법이 먼저다
- **이번에 식별된 CLI 결함의 적용** — 식별까지가 범위다(§9)
- npm 배포 / MCP 서버 / 두 번째 레지스트리 어댑터

## 2. 산출물

`ctreg` 저장소 안에 산다.

```
.claude-plugin/plugin.json          플러그인 매니페스트. mcpServers 키 없음
skills/ctreg/SKILL.md               한 페이지
docs/agent-field-test-2026-08-22.md 필드 테스트 결과 (실행 후 생성)
```

`plugin.json`은 스킬만 싣는다. MCP 서버는 이 프로젝트가 CLI로 대체한 것이므로 참조 구현의 매니페스트와 다르다.

## 3. SKILL.md 계약

### 3.1 말하는 것 — 규율만

1. **이 도구가 무엇인지** 한 문단. 임상시험 레지스트리를 하나의 정규화된 스키마로 조회한다는 것.
2. **가용성을 먼저 확인하라.** 플러그인은 `ctreg` 바이너리가 PATH에 있음을 보장할 수 없다(npm 미배포). 없으면 무엇을 해야 하는지 말한다.
3. **`ctreg registries`를 먼저 불러라.** 어떤 레지스트리가 무엇을 할 수 있는지가 거기 있다. 네트워크를 치지 않으므로 공짜다.
4. **표면은 `--help`가 말한다.**
5. **exit code로 분기하라.** 서로 다른 코드가 서로 다른 행동을 요구한다.
6. **`warnings[]`를 읽어라.** 조용히 좁혀지거나 잘린 것이 거기 적힌다.
7. **면책** — "이 도구의 출력은 임상시험 적격 판정이 아니다. 레지스트리 기재사항은 스크리닝을 대체하지 않는다."

### 3.2 일부러 말하지 않는 것

커맨드 목록, 플래그 목록, exit code의 의미 표, 경고 코드 목록, 출력 형식 설명. 전부 CLI가 스스로 말한다.

이것은 편의를 위한 생략이 아니라 **측정 장치**다. 스킬이 적어두면 에이전트가 그것을 쓸 뿐, CLI가 그 사실을 전달할 수 있는지는 알 수 없게 된다.

### 3.3 면책을 예외로 두는 이유

§3.2의 규칙에 예외가 하나 있다: 면책 문장은 CLI도 말할 수 있고 README에도 있지만 스킬에 넣는다.

에이전트가 안 배웠을 때 위험한 임상 주장을 하는지는 **일으켜서 발견할 종류의 결함이 아니다.** 실험의 순수성보다 안전 경계가 우선한다.

## 4. 시나리오

여섯 개. 각각 사람이 물을 법한 질문이고, 예상 실패는 에이전트에게 주지 않는다.

| # | 질문 | 몰리는 표면 | 예상 실패 |
| :-- | :-- | :-- | :-- |
| S1 | 서울 근처에서 모집 중인 비소세포폐암 시험이 있나? | `search` + `--near` + `--status` | 지명을 좌표로 못 바꿔 막힘 / 반경 밖 사이트를 보고 필터가 깨졌다고 판단 |
| S2 | 펨브롤리주맙 시험이 몇 건이고 phase 분포는? | `count` → `search` | `count`를 안 쓰고 페이지를 긁음 |
| S3 | NCT04280705가 유해사례를 보고했나? 심장 관련은? | `results` + `--ae-organ` | 요약을 완전한 것으로 읽음 |
| S4 | 이 세 NCT 정보를 정리해달라 (하나는 존재하지 않는 ID) | `get` 배치 | `not_found` 경고를 못 보고 3건이라 보고 |
| S5 | EudraCT 번호 2020-000001-11로 찾아달라 | 미지원 레지스트리 | exit 3을 "그런 시험 없음"으로 보고 |
| S6 | 결과가 게시된 완료된 당뇨 시험을 찾아달라 | 노출되지 않은 `hasResults` | 없는 플래그를 지어냄 |

S1·S3·S4·S5는 **오독하면 임상적으로 틀린 답**이 나오는 경로다. S2는 규율(count 먼저), S6은 한계 발견이다.

시나리오는 독립적이다 — 한 시나리오의 실패가 다른 시나리오를 막지 않는다. 순서에 의미는 없다.

### 4.1 전제 검증 (2026-08-22 실측)

각 시나리오가 의도한 표면에 실제로 닿는지 CLI 를 직접 돌려 확인했다.

| # | 실측 결과 |
| :-- | :-- |
| S1 | `--near Seoul` → exit 2, `error.code=usage`, 힌트 있음 |
| S3 | `results NCT04280705` → exit 0, AE `total 110 / expanded 0`, 경고 `results_summarized` |
| S4 | `get NCT04280705 NCT99999999` → exit 0, 1건 반환, 경고 `not_found` |
| S5 | `get EUCTR:2020-000001-11` → exit 3, `error.code=unsupported` |
| S6 | `--help` 에 `has-results` 플래그 없음 — 전제 성립 |

**S3 와 S4 가 이 실험의 핵심이다.** 둘 다 exit 0 이고, 경고를 읽지 않으면 각각 "유해사례 110건을 확인했다" 와 "두 시험을 모두 찾았다" 로 읽힌다. 도구는 사실을 말했고, 그것을 읽지 않는 것은 조용히 틀린 답이 된다. SILENT-WRONG(§6)이 나온다면 여기일 가능성이 가장 높다.

## 5. 서브에이전트 브리핑 계약

### 5.1 주는 것

- 사용자 질문 한 줄 (§4의 질문 그대로)
- `skills/ctreg/SKILL.md` 경로
- `ctreg` 바이너리를 쓸 수 있다는 사실과 그 실행 방법
- 별도 `CTREG_CACHE_DIR` (시나리오 간 캐시 오염 방지)

### 5.2 주지 않는 것 — 이것이 실험의 통제 조건

- **저장소 소스를 읽지 못한다.** `src/`, `tests/`, `docs/`(스킬 제외) 접근 금지. 읽으면 도구의 자기설명이 아니라 소스에서 답을 얻고 실험이 무의미해진다.
- 예상 실패, 시나리오의 의도, 다른 시나리오의 존재
- CLI 내부 구조에 대한 어떤 설명도

### 5.3 반환하는 것

1. 실행한 모든 커맨드와 그 출력 (축어)
2. 사용자 질문에 대한 최종 답 — 사용자에게 말하듯이
3. 헤맨 지점: 무엇을 하려다 무엇 때문에 막혔거나 돌아갔는지
4. 확신이 없는 지점: 답했지만 스스로 미심쩍은 부분

4번이 중요하다. 에이전트가 스스로 미심쩍다고 말한 것과 자신만만하게 틀린 것은 다른 발견이다.

## 6. 판정 프레임

각 헤맨 지점과 각 최종 답을 네 갈래 중 하나로 판정한다. 판정은 컨트롤러가 하고, 근거를 함께 기록한다.

| 범주 | 뜻 | 처리 |
| :-- | :-- | :-- |
| **CLI-FIX** | 도구가 스스로 말했어야 하는데 못 말했다 | 식별만. 적용은 범위 밖(§9) |
| **SKILL-TEACH** | 도구가 구조적으로 말할 수 없다 | 스킬에 추가 |
| **AGENT** | 도구도 스킬도 멀쩡했다 | 기록만 |
| **SILENT-WRONG** | 답이 틀렸는데 에이전트가 몰랐다 | 최우선. CLI-FIX 또는 SKILL-TEACH로 세분 |

**SILENT-WRONG이 이 작업의 존재 이유다.** CLI 설계 전체가 "실패했는데 성공처럼 보이는 것"을 막으려 만들어졌는데, 에이전트가 실제로 안 속는지는 확인된 적이 없다. 이 범주가 없으면 모든 발견이 사용성 문제로 뭉개진다.

판정 시 SILENT-WRONG은 다른 세 범주와 배타적이지 않다 — 틀린 답은 그 원인에 따라 CLI-FIX이거나 SKILL-TEACH다. SILENT-WRONG은 심각도 표시이지 원인 분류가 아니다.

## 7. 결과 문서

`docs/agent-field-test-2026-08-22.md`. API 필드 테스트(`docs/field-test-2026-08-22.md`)와 같은 형식을 따른다 — 그 문서가 판정 열이 자기 기대를 검사하지 않아 한 번 고쳐졌으므로, 같은 실수를 반복하지 않는다.

시나리오마다:
- 질문
- 에이전트가 실행한 커맨드 목록 (전사는 부록)
- 최종 답 요약
- **답이 옳았는가** — 실제 CT.gov 데이터와 대조한 판정. "에이전트가 답을 냈다"가 아니라 "그 답이 맞았다"
- 헤맨 지점과 각각의 범주 판정

그리고 종합:
- CLI-FIX 목록 (다음 작업의 입력)
- SKILL-TEACH 목록 (이번에 스킬에 반영)
- SILENT-WRONG 건수 — 0이 아니면 그 자체가 헤드라인

## 8. 스킬의 성장

필드 테스트 후 SKILL.md는 SKILL-TEACH로 판정된 항목만큼 자란다. **관찰된 것만 넣는다** — "이것도 가르치면 좋겠다"는 추측은 넣지 않는다. 추측으로 채우면 다음 필드 테스트가 다시 무의미해진다.

성장한 스킬은 원 검토 문서가 권고한 모양(규율 + 오독 방지)에 가까워질 것으로 예상하지만, 그것은 예측이지 목표가 아니다.

## 9. 범위

**포함**

1. `.claude-plugin/plugin.json` + `skills/ctreg/SKILL.md` (§3의 얇은 판)
2. 시나리오 6개 실행 (§4, §5의 브리핑 계약대로)
3. 판정 (§6) 및 결과 문서 (§7)
4. SKILL-TEACH 항목의 스킬 반영 (§8)

**제외**

- CLI-FIX의 적용. 몇 개가 얼마나 큰지 보고 별도로 결정한다. 지금 "다 고친다"고 하면 범위가 열린다.
- 슬래시 커맨드, 워크플로 스킬, npm 배포
- 슬라이스 2 선결 조건(`docs/slice-2-prerequisites.md`) — 무관하다

**완료 조건**

- 시나리오 6개 전부 실행되고 각각 전사·최종 답·판정이 기록됨
- 모든 헤맨 지점이 네 범주 중 하나로 판정됨
- 각 최종 답이 실제 데이터와 대조되어 옳고 그름이 판정됨
- SKILL.md가 SKILL-TEACH 항목만큼 자람
- CLI-FIX 목록이 다음 작업의 입력으로 남음

## 10. 위험

| 위험 | 완화 |
| :-- | :-- |
| **얇은 스킬로 에이전트가 아예 못 굴러 시나리오가 조기 종료된다** | 그 자체가 최상급 CLI-FIX 발견이다. 다만 여섯 개가 전부 같은 지점에서 죽으면 정보량이 없으므로, 첫 시나리오를 먼저 돌려 확인한 뒤 나머지를 돌린다 |
| **서브에이전트가 소스를 읽어 실험이 오염된다** | 브리핑에 명시하고, 반환된 전사에서 소스 접근 흔적을 확인한다. 읽었으면 그 시나리오는 무효 처리하고 다시 돌린다 |
| **내가 브리핑한 에이전트는 순진한 사용자가 아니다** | 사실이다. 이 방법으로 잡을 수 없는 것이 있음을 결과 문서에 명시한다. 실제 사용자 세션은 별도 작업이다 |
| **판정이 자의적이 된다** | 각 판정에 근거를 함께 적는다. "CLI가 이것을 말할 수 있었는가"는 대체로 확인 가능한 질문이다 — `--help`, `registries`, 에러 힌트에 있었는지 보면 된다 |
| **CT.gov 데이터가 바뀌어 "옳은 답"의 기준이 흔들린다** | 대조 시점을 기록한다. 총계 같은 값은 변하므로 자릿수 수준으로 판정하고, 존재/부재 같은 사실만 엄격히 본다 |

## 11. 다음 단계

이 문서는 설계다. 구현 계획(작업 분할, 순서, 수용 기준)은 별도 문서로 작성한다.
