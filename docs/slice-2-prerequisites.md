# 슬라이스 2 착수 전 선결 조건

- **일자:** 2026-08-22
- **성격:** 최종 전체 브랜치 리뷰가 남긴 항목 중, **두 번째 어댑터를 쓰기 전에** 처리해야 하는 것들.
  "언젠가" 목록이 아니다. 전부 하나의 어댑터로는 보이지 않고, 두 번째가 오는 순간 문다.

최종 리뷰는 `isrctn` 스텁 어댑터를 실제로 만들어 테제를 검증했다 — `src/cli/` 아래 어떤 파일도
고치지 않고 컴파일된다. 심은 진짜다. 아래는 그 위에 남은 세금이다.

## 반드시 먼저

### 1. `FetchOpts.caps` 가 캡 정책을 나르지 않는다 (최종 리뷰 I3)

`caps.outcomes` 는 아무도 읽지 않고, `caps.locations` 는 어댑터가 덮어쓴다. 문서화된 채널을
성실히 따르는 어댑터 #2 는 스펙 §5.2 를 양방향으로 어긴다. `CAPS.outcomes.default` 가 죽은
상수인 것(이연 #16)이 같은 문제의 증상이다 — 상수만 지우면 채널이 망가졌다는 증거가 사라지므로
둘을 함께 고친다.

관련: `src/cli/args.ts`(caps 조립), `src/adapters/ctgov/map.ts`(캡 적용), `src/core/query.ts`.

### 2. 선언되었으나 소비자가 없는 `limits` (최종 리뷰 I5)

`limits.maxPageSize`, `limits.ratePerSec`, `search.geoNeedsCoords` 는 capability 에 선언되지만
코드 어디에서도 읽히지 않는다. 특히 `ratePerSec` — 스펙 §6.2 는 레지스트리마다 예산이 다르다고
하는데 런타임은 전역 요청률 하나를 쓴다. 어댑터 #2 가 다른 예산을 선언해도 무시된다.

### 3. `Record<RegistryKey, RegistryAdapter>` 의 전체성 (최종 리뷰 I7)

다섯 커맨드 시그니처가 전체 `Record` 를 요구해서, 스펙이 계획한 "심만 비워 둔다"(키는 등록하되
어댑터는 아직 없음)를 타입이 금지한다. 측정된 비용은 테스트 호출 지점 10곳. 코드의 네 군데
`adapters[key]!` 가 그 증상이다.

### 4. 계약 스위트의 두 공백 (최종 수정 웨이브 재리뷰)

스위트는 이제 네 메서드를 stub 전송으로 구동하고 여섯 가지 사보타주를 잡는다. 남은 것:

- **경고를 전부 버리는 어댑터가 통과한다.** 스위트가 경고의 *모양* 은 검사하지만 *존재* 는
  검사하지 않아, 조용히 절단하는 어댑터가 적합 판정을 받는다.
- **`--raw` 의 `source` 가 좁혀진 어댑터가 통과한다.** *없는* source 만 잡는다.
  하네스의 `respond(url)` 이 이미 업스트림 본문을 쥐고 있으므로, `rec.source` 가 해당 스터디와
  깊은 동등인지 요구하면 닫힌다.

## 알아두고 결정할 것

### `count` 가 겹치는 레지스트리의 총계를 합산한다 (최종 리뷰 I6)

`count.ts:45` 의 `total += r.data`. 레지스트리가 둘 이상이고 같은 시험이 양쪽에 등록돼 있으면
합계는 무엇의 개수도 아니다. 교차 등록은 흔하다(`crossIds` 가 존재하는 이유). 레지스트리별
개수만 내고 합계를 내지 않는 것도 정당한 선택이다.

### `filter.ids` 배치 상한

실측 결과 CT.gov 는 최소 500개를 받는다(`docs/field-test-2026-08-22.md`). 그러나 `maxBatchIds`
를 올리려면 **`get` 이 배치 내부 페이지네이션을 먼저 구현해야 한다** — `buildIdsParams` 가
`pageSize` 를 `CAPS.pageSize.max`(200)로 두고 `get` 은 한 페이지만 읽으므로, 500개 청크는
500개를 묻고 200개를 받아 그것이 전부인 양 반환한다. 계약 스위트가 이 불변식을 강제한다.

### `AREA[HasResults]true`

문법은 필드 테스트로 확인됨(79,794건). 슬라이스 1 에서는 **결정에 의해** 미노출 —
동작하지 않아서가 아니다.

## 필드 테스트가 드러낸 CLI 결함

`docs/agent-field-test-2026-08-22.md` 의 여섯 에이전트 필드 테스트에서 CLI-FIX 로 판정된
일곱 건(F1–F7)과 미해결로 남긴 O2. 각 항목에 어느 시나리오에서 어떻게 드러났는지를 붙인다 —
근거 없는 항목은 우선순위를 매길 수 없다. 우선순위는 원장이 매긴 순서를 그대로 따른다:
F7 → F1 → F4 → F2·F5 → F6·F3.

**F1·F2·F4·F5 는 하나의 패턴이다.** 능력 선언이 존재만 말하고 적용 범위(내용)를 말하지
않으면, 에이전트는 그 한도를 실제로 부딪혀서만 알게 된다. 부딪힌 것을 알아채지 못하면
조용히 틀린 답을 낸다. 넷을 따로 고치면 패턴 자체는 남아 다음 항목에서 다시 나타난다.

### F7 — 파이프가 일찍 닫히면 크래시한다

S6(결과가 게시된 완료 당뇨 시험)에서 드러남. exit 1(계약에 없는 코드)과 원시 스택트레이스를
낸다. 결정적이고 100% 재현되며 흔한 사용에서 터진다 — 가장 싸고 가장 확실해서 1순위다.

### F1 — `--location` 이 매칭된 사이트를 결과에서 잘라낸다

S1(서울 근처 모집중 NSCLC)에서 드러남. `--near` 는 같은 정보를 보존하는데 `--location` 은
버리고, 두 경로의 차이를 말하는 것이 도구 안에 없다. 이번 에이전트는 파고들어 직접
확인하고 하한선으로 정직하게 답했지만, 임상적 결과가 가장 크다 — 다음 에이전트가 같은
데까지 파고든다는 보장이 없다.

### F4 — 경고가 존재하지 않는 복구 경로를 암시한다

S4(세 NCT 정리, 하나는 없는 ID)에서 드러남. "잘렸다"만 말하고 "되찾을 수 없다"를 말하지
않아, 에이전트가 없는 해결책을 사용자에게 권했다. F1 과 같은 뿌리 — 경고가 오독을 막는
대신 새 오독을 만든다.

이 항목의 일부는 이미 이 문서 안에 있다. `filter.ids 배치 상한`(아래, `## 알아두고 결정할 것`)이
적어둔 "500개를 묻고 200개를 받아 그것이 전부인 양 반환한다"가 F4 가 실제로 부딪히는
자리이고, 그 근본 원인은 위의 `2. 선언되었으나 소비자가 없는 limits`(최종 리뷰 I5)다.
새 항목으로 쪼개지 말고 I5 를 고칠 때 F4 를 함께 검증한다 — 둘을 따로 고치면 둘 다 반쯤
고쳐지고 끝난다.

### F2 — 능력 선언이 적용 범위를 말하지 않는다

S5(EudraCT 번호로 조회)에서 드러남. `term: true` 는 축의 존재만 선언한다. 0건이 "없음"인지
"안 봄"(그 축을 지원하지 않아 아예 보지 않음)인지 판별할 근거가 도구 안에 없다.

### F5 — 값 어휘를 열거할 방법이 없다

S2(펨브롤리주맙 건수와 phase 분포)에서 드러남. 에이전트가 틀린 값을 일부러 넣어 힌트를
캐냈고, 나머지는 추측했다. F2 와 같은 뿌리 — 선언이 내용을 말하지 않는다.

### F6 — `results_summarized` 가 부분 전개를 구분하지 않는다

S3(NCT04280705 유해사례, 심장 관련)에서 드러남. 전개 전과 부분 전개가 같은 경고 코드를
쓴다. 마찰이지 오답은 아니다 — 에이전트는 안 빠졌다.

### F3 — 서브커맨드별 `--help` 가 없다

세 시나리오가 부딪힘. 최상위 `--help` 와 바이트 단위로 동일해 서브커맨드 전용 옵션을
확인할 방법이 없다. 마찰이지 오답은 아니다.

### O2 — 미해결: 재현되지 않는 `data: null`

두 번 관찰, 세 가설 기각, 재현 실패. 결함으로 확정하지 않는다 — 재현하지 못한 것을
확정하면 필드 테스트 문서 전체의 신뢰도가 흔들린다. 다음 필드 테스트에서 재현을 다시
시도한다.

### `AREA[HasResults]true` 와 S6 의 관계

S6 의 질문("결과가 게시된 완료 당뇨 시험")은 위 `AREA[HasResults]true` 항목이 다루는 축과
주제가 겹친다. 다만 필드 테스트 원장은 S6 가 실제로 이 문법을 썼는지 기록하지 않아 단정할
수 없다. 슬라이스 2 에서 이 문법의 노출 여부를 결정할 때 S6 를 참고 시나리오로 다시
확인한다.

## 두 번째 어댑터 후보

**ISRCTN** 이 1순위다. 인증 없는 공개 REST API 이고, 조사에서 `studyType`·`hasResults`·`crossIds`
를 포함한 core 필드 대부분이 확인됐다(`docs/registry-field-survey-2026-08-22.md`).
EU CTIS 와 jRCT 는 공개 API 를 찾지 못했다(화면만).

## 조사에 남은 미확인 질문

- **ICTRP 의 "final sample size" 가 실제로 채워지는가.** TRDS 항목 17 의 명칭이
  "Target & final sample size" 라 실제치도 담을 수 있으나 미확인. 확인 방법은 조사 문서에 기록됨.
- **CTIS 의 `Last update` 가 레코드별인가 회원국별인가.** 같은 "Member State" 블록 안에 있으나
  정의문에 회원국별 문구가 없다. `status` 와 같은 구조적 문제일 수 있다.

## 이연된 사소한 항목

- `count.ts` 의 미지원 봉투가 `data: {total: 0}` 을 남긴다(`results.ts` 는 `data: null`) —
  상태를 안 보는 호출자가 0 을 본다.
- `tests/runtime/http.test.ts` 의 헬퍼 기본 인자가 `CacheMode` 유니온을 인라인으로 반복한다.
- `--raw` 로 전체 문서를 받을 때 페이로드 경고가 없다(`results --full` 은 `results_full` 을 낸다).
- `sponsor` 가드가 한 분기에서 `lead: ""` 를 낼 수 있다(반대 방향은 수정됨).

## 검증 방법에 대한 교훈

슬라이스 1 에서 값비싼 결함들이 어떻게 잡혔는지의 기록. 다음 슬라이스에도 그대로 적용된다.

**일괄 변환은 변환되지 않은 형태로 검증한다.** `grep -c <새 형태>` 는 있는 것을 세므로
놓친 것을 원리상 드러낼 수 없다. `grep -n <옛 형태>` 가 0건이어야 한다.
스키마를 strict 로 전환하면서 중첩 6개를 놓친 채 "검증됨" 으로 통과한 원인이 정확히 이것이다.
그 6개 중 하나 때문에 잘린 적격 기준문이 완전한 것으로 읽히고 있었다.

**읽지 말고 실행한다.** 이 슬라이스의 Critical 대부분은 코드를 읽어서는 나오지 않았다 —
실제 입력을 스키마에 통과시켜(`criteriaTruncatd` 오타가 삼켜지는 것), 인용한 URL 을 직접 열어
(조사 문서의 주장), 구현을 변이시켜(값 변이 20개가 전부 생존 — 테스트가 값을 전혀 고정하지
않고 있었다), 어댑터를 사보타주해서(계약 스위트가 "search 가 항상 던지는" 어댑터를 통과시키던 것)
나왔다.

**브리프의 테스트를 구현 전에 돌린다.** 계획 버그 4건이 이 규율로 잡혔다 — 전부 브리프의
테스트와 브리프의 샘플 코드가 서로 모순인 경우였다. 다만 이것으로 잡을 수 없는 종류가 있다:
테스트와 코드가 서로는 일치하는데 권위(참조 구현·스펙)와 어긋나는 경우. 그건 리뷰어가 권위를
직접 열어봐야 나온다.

**"형제 코드가 맞으니 이것도 맞겠지" 를 받아들이지 않는다.** 이 프로젝트에서 두 번 틀렸다 —
strict 이 형제 스키마에는 적용됐는데 중첩만 빠졌을 때, 락 규율이 다른 경로에는 맞았는데 한 경로만
밖에 있었을 때. 구조적으로 동일해 보이는 것을 확인 없이 통과시키지 않는다.

**정확하지만 미검증인 동작은 지연된 결함이다.** 리뷰어가 프로브로 정확성을 증명해도, 출하되는
스위트가 그것을 붙들지 않으면 다음에 그 코드를 손대는 사람이 녹색 스위트를 보면서 조용히 깨뜨린다.
네트워크 클라이언트의 실패 경로가 특히 그렇다 — 실전에서 가장 많이, 테스트에서 가장 적게 실행된다.
