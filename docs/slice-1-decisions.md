# 슬라이스 1 설계 결정 기록

- **일자:** 2026-08-22
- **범위:** `ctreg` 슬라이스 1 (Task 0–16, 53커밋)
- **성격:** 구현 중 내려진 결정과 그 근거. 코드는 *무엇을* 하는지 말하지만 *왜* 그렇게 하는지는
  말하지 않는다. 여기가 그 자리다.

각 항목은 `결정 — 근거 — 틀렸을 때의 비용` 형식이다. 되돌리고 싶은 결정이 있으면 비용 항목이
무엇을 다시 해야 하는지 알려준다.

## 이 기록이 나온 방식

계획을 서브에이전트에 태스크 단위로 넘기고, 각 태스크마다 구현 → 리뷰 → 수정 라운드 → 재리뷰를
돌렸다. 리뷰어에게는 코드를 읽지 말고 **실행해서** 확인하라고 요구했다 — 스키마에 실제 입력을
통과시키고, 인용한 URL을 직접 열고, 구현을 변이시켜 테스트가 잡는지 보고, 어댑터를 사보타주해
계약 스위트가 걸러내는지 확인하는 식이다.

그 결과 잡힌 결함 중 상당수가 **계획 자체의 결함**이었고, 여러 건은 테스트가 녹색인 상태로
존재했다. 아래 룰링의 상당수가 그 발견에 대한 응답이다.

---

Ruling R1: T4 의 `query.ts` / `capability.ts` 가 T9(pageToken)·T10(near)·T12(nextPageToken) 에서
  확장되는 것은 계획된 점진 구축이지 T4 의 결함이 아니다 — 각 확장 태스크가 명시적 Modify 스텝을
  갖고 있다 — 틀렸을 때 비용: T4 리뷰어가 "불완전한 타입" 으로 오탐할 수 있으므로 T4 의 리뷰
  프롬프트에 이 사실을 사실로 기재한다(오탐 억제 지시가 아니라 컨텍스트 제공).

Ruling R2: T1 의 package.json `bin` 을 처음부터 `{"ctreg": "dist/cli/bin.js"}` 로 둔다 —
  실제 진입점은 T14 가 만드는 bin.ts 이고, T1 의 index.js 값은 어느 시점에도 유효하지 않다 —
  틀렸을 때 비용: T1 구현자가 계획 텍스트와 다른 값을 쓰므로 dispatch 에 명시해야 하고,
  빠뜨리면 T14 에서 고치게 되어 한 라운드가 는다.

Ruling R3: Task 0 리뷰와 Task 1 구현을 병렬로 돌린다 — Task 1 이 Task 0 에 의존하는 것은
  "폐쇄 어휘·스키마 변경 여부" 하나뿐이고 그 판정("변경 없음")은 이미 확정·커밋되었다(a82d631).
  Task 0 리뷰가 찾을 수 있는 것은 조사 문서 자체의 결함뿐이며 Task 1 이 만드는 파일과 겹치지 않는다.
  구현 서브에이전트 병렬 금지 규칙에도 저촉되지 않는다 — Task 0 의 구현자는 이미 끝났고 남은 일은
  보고서 파일 작성뿐이다 — 틀렸을 때 비용: 리뷰가 어휘 변경을 요구하면 core/vocab.ts 한 파일을
  고치는 소규모 재작업. 직렬로 기다렸을 때 잃는 왕복 한 번보다 싸다.

Ruling R4: 보고서 파일이 두 번째 요청에도 오지 않으면, 커밋된 조사 문서
  (docs/registry-field-survey-2026-08-22.md, 방법론·`?` 사유·판정 근거를 모두 담고 있다)를
  리뷰 입력으로 삼고 누락을 원장에 남긴 채 진행한다 — 틀렸을 때 비용: 실패한 시도(막힌 사이트,
  빈 검색) 기록이 유실되어 나중에 같은 땅을 다시 밟을 수 있다. 조사 문서가 실질을 담고 있어 감수 가능.

Ruling R5: Task 2 는 Task 1 리뷰가 끝난 뒤 dispatch 한다 — Task 2 가 만드는 errors.ts/exit-codes.ts 는
  Task 1 산출물과 파일이 겹치지 않지만, Task 1 수정 라운드와 동시에 돌면 두 프로세스가 같은 저장소에
  커밋해 git index.lock 충돌을 낼 수 있다 — 틀렸을 때 비용: 왕복 한 번의 지연. R3 의 병렬화는
  느린 웹 조사 리뷰를 가렸기에 값이 있었지만, 여기서는 가릴 만한 긴 작업이 없다.

Ruling R6: phase 테스트 Important 발견을 수용하고 계획 텍스트를 고친다 — 문제의 테스트는 계획에서
  그대로 옮긴 것이지만, 계획의 phase 테스트는 자기 자매 테스트 둘보다 약하고 이는 의도가 아니라
  계획의 누락이다. 구속력 있는 권위인 스펙 §2.3 이 TRIAL_PHASE 를 정확히 7개로 고정하고 Task 8 의
  PHASE_IN 매핑표가 그 7개를 정확히 덮어야 하므로, 집합을 고정하지 않는 테스트는 스펙을 덜 검사한다.
  값이 하나 빠져도 테스트가 아니라 오매핑된 임상시험 phase 로 드러난다 — 틀렸을 때 비용: 거의 없음.
  테스트 한 줄이 엄격해질 뿐이고 status 테스트는 toHaveLength(10) 으로 이미 충분해 범위를 넓히지 않았다.

Ruling R7: Task 0 리뷰가 보고서 파일을 못 봤다고 보고했으나(존재함, 24.9KB — 리뷰어의 ls 가 내 통지보다
  앞섰거나 통지 후 재확인하지 않았다) 리뷰를 다시 돌리지 않는다 — 보고서가 기여했을 검사는 `?` 사유와
  dead-ends 의 교차 대조인데, 리뷰어는 그 대신 1차 출처 5건을 직접 검증했다. 구현자의 자기 진술을
  대조하는 것보다 출처를 직접 여는 쪽이 더 강한 증거다 — 틀렸을 때 비용: 시도조차 안 한 항목이 "확인 불가"로
  위장된 경우를 놓칠 수 있다. 다만 리뷰어가 ISRCTN 의 `?` 판정들을 1차 문서로 되짚어 확인해 그 위험은 낮다.

Ruling R8: ICTRP 의 "final sample size" 실제 채워짐 여부를 지금 확인하지 않는다 — 답이 필요한 시점은
  ICTRP 어댑터를 만들 때(슬라이스 2 이후)이고, 지금 필요한 것은 주장을 증거에 맞게 좁히는 것이다 —
  틀렸을 때 비용: 없음. 열린 질문으로 정확히 기록되면 나중에 그 자리에서 확인된다.

Ruling R9: 무응답 재리뷰어를 판정 없음으로 처리하고 sonnet 으로 새 재리뷰어(`task1-rereview2`)를 띄운다.
  침묵한 리뷰는 승인이 아니다. 내가 직접 diff 를 읽고 확인했더라도 컨트롤러 자체 검증은 리뷰를 대체하지
  못한다 — 틀렸을 때 비용: 아주 작은 diff 에 리뷰 좌석 하나를 더 쓴다. 검증되지 않은 수정을 통과시키는
  것보다 싸다. 남은 태스크의 재리뷰는 haiku 를 쓰지 않는다.

Ruling R10: Task 0 수정 라운드(docs/ 만 건드림)와 Task 2 구현(src/·tests/ 만 건드림)을 병렬로 돌린다 —
  파일이 완전히 분리되어 있고 공유 자원은 .git/index 뿐이다. Task 2 디스패치에 index.lock 충돌 시
  재시도를 명시해 그 유일한 위험을 덮는다 — 틀렸을 때 비용: 커밋 한 번 재시도. R5 를 이 조건에서 완화한다.

Ruling R11: 비행 중인 수정 라운드 1 을 수정 지시한다 — 내 Finding 2("phase/ICTRP 기호를 고쳐라")가
  틀렸음이 리뷰 갱신으로 드러났다. 구현자의 X-vs-~ 기준은 타당했고 진짜 결함은 그 근거가 아무도 열지 않을
  보고서에만 있다는 것이다. 알려진 오지시를 실행시킨 뒤 되돌리는 것보다 실행 전 정정이 싸다 —
  틀렸을 때 비용: 라운드 경계가 흐려져 재리뷰 범위가 커진다. 되돌릴 변경을 만드는 것보다 낫다.

Ruling R12: Finding 6 에 한해 무-fetch 제약을 푼다 — ISRCTN default XML 한 번 호출로 `?` 3개가 해소되고,
  ISRCTN 은 인증 없는 공개 REST 라 두 번째 어댑터 1순위다. 그 세 칸은 슬라이스 2 에서 실제로 쓰인다 —
  틀렸을 때 비용: 요청 한 번과 몇 분. 실패해도 정직하게 기록하면 그 자체로 유효한 결과다.

Ruling R13: phase/ICTRP 를 `~` 로 되돌리지 않고 `X` 를 수용한다 — R11 의 목적은 X-vs-~ 기준이
  아무도 열지 않을 보고서가 아니라 조사 문서 본문에 있게 하는 것이었고, 구현자는 다른 기호에 도달하면서도
  그 기준을 셀 각주에 명시하고 Step 3 재집계(5/6)를 명시적으로 적었다. 목적은 달성됐다. 기호를
  되돌리는 것은 결과보다 내 앞선 지시를 우선하는 churn 이다 — 틀렸을 때 비용: 두 판정 기준 중 하나를
  택한 것뿐이고, 어느 쪽이든 문서가 자기 기준을 밝히고 일관되게 적용하면 족하다. 판정에는 영향 없음(5/6 도 규칙 충족).

Ruling R14: 발견을 수용하고 계획의 설계를 바꾼다 — 코드는 계획에서 그대로 옮긴 것이므로 내 결함이다.
  이 프로젝트의 테제 전체가 "두 번째 레지스트리 추가는 격리된 한 번의 변경" 이고, 그것이 이 CLI 와
  CT.gov 래퍼를 가르는 유일한 차이다. 조용히 desync 될 수 있고 두 경로가 desync 의 의미에 대해 서로
  다르게 반응하는 확장점은, 하필 그것이 시험되는 순간에 — 1년 뒤 주석을 믿는 사람에 의해 — 테제를 무너뜨린다.
  지시한 해법: ID_PATTERNS 를 Record<RegistryKey, …> 로 바꿔 desync 를 컴파일 오류로 만든다.
  제약: REGISTRY_KEYS 는 리터럴 튜플로 유지해야 한다(Task 4 의 z.enum 이 [string, ...string[]] 을 요구) —
  틀렸을 때 비용: 파일 하나의 소규모 리팩터. 검증은 가짜 키를 넣어 tsc 가 실패하는 것을 축어로 붙이는 것.

Ruling R15: ⚠️(RED 증거 미검증)를 실제 결함으로 승격하지 않는다 — 같은 구현자가 Task 3 의 GREEN 과 tsc 를
  실제 출력으로 붙였고, Task 1·2 구현자들도 축어 증거를 냈다. 과거를 재현시키는 대신 이후 축어 붙여넣기를
  요구하는 편이 싸다 — 틀렸을 때 비용: RED 가 다른 이유로 실패했을 가능성이 미검증으로 남는다.
  테스트가 구현 없이 통과할 수 없는 구조(모듈 import)라 위험은 낮다.

Ruling R16: R13 을 폐기하고 현재 상태(`~` + 「방법과 한계」의 일반 규칙)를 수용한다 — R13 은
  "기호를 되돌리는 것은 churn" 이라는 판단이었으나, 구현자가 기호를 되돌리면서 X/~ 기준을 특정 셀의
  예외가 아니라 문서 전체에 적용되는 일반 규칙으로 승격시켰다. 그 결과가 X + 인라인 예외보다 낫다 —
  틀렸을 때 비용: 없음. 판정(6/6)도 규칙을 충족한다.
  Finding 6 성과: ISRCTN default XML 실호출(ISRCTN96189403)로 studyType/hasResults/crossIds 세 칸이
  `?`→O. 각각 <primaryStudyDesign>, <results>, <externalRefs> 로 근거 명시. Step 3 는 3/6→4/6.
  ISRCTN 이 두 번째 어댑터 후보로서 필드 커버리지까지 확인된 셈이다.
  치験の区分 도 JPMA 가이드 15쪽 인용으로 뒷받침됨(추론 아님).

Ruling R17: Task 0 재리뷰를 기다리지 않고 Task 4 를 dispatch 한다 — Task 4 는 스펙 §2.2/§2.3 의 타입을
  구현하고, Task 0 이 그 부분에 "변경 없음" 판정을 내렸으며 그 판정은 첫 리뷰에서 이미 독립 검증됐다.
  남은 재리뷰는 이미 식별된 발견들의 수정 품질을 판정하는 것이고 그 중 어느 것도 core/detail 경계를
  건드리지 않는다 — 틀렸을 때 비용: 재리뷰가 게이트 결론을 뒤집으면 record.ts 수정. 가능성 낮음.

Ruling R18: Task 12(nextPageToken), Task 9(pageToken), Task 10(near) 가 나중에 추가하도록 계획된 세 필드를
  Task 4 에서 미리 넣는다 — 어차피 필요한 것이 확정돼 있고, 계약 파일을 세 번 더 여는 것보다 한 번에
  완성하는 편이 낫다. R1 은 점진 구축이 결함이 아니라고 판정했을 뿐 그것이 최선이라고 하지 않았다 —
  틀렸을 때 비용: Task 4 의 표면이 브리프보다 조금 넓어져 리뷰어에게 그 사실을 알려야 한다.

Ruling R19: 부록 커밋 cff48a8(CTIS dates.lastUpdated `?`→`~`)에 정식 verdict 없이 진행한다 —
  라운드 2 의 선택 항목이었고 여섯 발견 중 어느 것도 아니며, 게이트 판정에 영향이 없다
  (dates.lastUpdated 는 이미 확정 4곳). 재리뷰어가 skim 후 내부 정합성을 확인했고 나도 diff 를 직접 읽어
  과잉 주장이 없음을 봤다. 최종 전체 리뷰로 이월한다 — 틀렸을 때 비용: 조사 문서 한 칸의 기호가
  약간 과/소 진술될 수 있다. 코드에도 게이트 결론에도 영향 없음.

Ruling R20: R19 를 폐기한다 — 재리뷰어가 부록을 결국 판정했고(PARTIALLY ADDRESSED) 지적이 옳다.
  근거와 hedge 자체는 PDF 직접 확인으로 검증됐으나, "확인 못한 항목 요약" 에서 CTIS 행이 통째로
  사라졌다. 스코프(레코드별 vs 회원국별)라는 열린 하위 질문이 남아 있는데도. Finding 1 의 수정이
  이미 같은 형태의 선례를 만들었다: enrollment.count/ICTRP 는 매트릭스에서 `O` 지만 하위 질문이
  열려 있어 그 표에 행을 유지한다. 각주에만 사는 열린 질문은 실무적으로 닫힌 질문이고, 그 표는
  미래 어댑터 작성자가 "무엇이 아직 모르는가" 를 찾으려 훑는 곳이다 — 틀렸을 때 비용: 거의 없음.
  한 행 추가.

Ruling R21: NormalizedQuery 에서 `page?: number` 를 제거한다 — CT.gov 는 불투명 커서로만 페이지네이션하고
  페이지 번호 파라미터가 아예 없어 이 필드는 중복이 아니라 구현 불가다. 남겨두면 두 가지로 실패한다:
  어댑터 작성자가 존중하려다 못 하거나, CLI 에 아무 일도 안 하는 --page 플래그가 생긴다. 계약의 필드는
  무언가가 그것을 채울 수 있다는 약속이다. 계획이 CT.gov 페이지네이션을 확인하기 전에 쓰였고, 이후
  스펙 정정이 pageToken 을 추가하면서 대체된 필드를 지우지 않았다 — 틀렸을 때 비용: 없음.

Ruling R22: 계약 스키마들을 strict 로 만든다 — 기본 stripping 하에서는 어댑터가 locationsTotal 을
  locationTotal 로 오타 내면 의도한 필드가 없는 레코드가 나오고, 그 필드가 optional 이라 스키마가 통과시킨다.
  오타가 조용한 데이터 손실이 되고, 이 도메인에서 그것은 호출자에게 "이 시험은 사이트가 없다" 로 읽힌다.
  무엇이든 추가로 받아들이는 스키마는 자기가 존재하는 이유인 그 검사를 수행할 수 없다. 레지스트리별
  부가 데이터는 애초에 정규화 레코드에 실리면 안 되고 `source`(--raw 전용)가 그 자리다 — 틀렸을 때 비용:
  나중 태스크가 정당한 필드를 추가할 때 스키마도 고쳐야 한다. 스키마가 곧 계약이므로 그게 옳은 동작이다.

Ruling R23: Minor 로 등급된 "CAPS 에 테스트 없음" 을 수정 라운드로 승격한다 — CAPS 는 잘못된 숫자 하나가
  프로젝트 전체의 바운딩을 바꾸는 유일한 지점이고, 이를 소비하는 태스크들이 CAPS 자체에 대해 단언하므로
  틀린 값이 잡히는 대신 동어반복으로 확인된다. R6(스펙 고정 상수는 테스트로 고정해야 한다)과 같은 형태다 —
  틀렸을 때 비용: 테스트 하나. 일관성을 지키는 편이 낫다.

Ruling R24: 손상된 버킷의 복구값을 0 이 아니라 now+intervalMs 로 바꾼다 — 파싱 불가는 "마지막 요청이
  언제였는지 모른다" 는 뜻이고, 0 은 가장 약한 증거에서 가장 강한 주장("지금 가라")을 낸다. 읽을 수 없는
  버킷의 대가는 한 간격이어야지 모든 프로세스에 대한 즉시 접근이어서는 안 된다 — 틀렸을 때 비용: 손상
  발생 시 1초 지연. 이 파일이 막으려는 것이 정확히 thundering herd 다.

Ruling R25: lockTimeoutMs 를 정직한 이름으로 바꾼다(lockRetryMaxMs) — Task 7 이 아직 없어 지금은 공짜이고,
  두면 "이만큼 뒤 포기" 로 읽히는 파라미터가 세 태스크 뒤에 버그를 만든다 — 틀렸을 때 비용: 브리프의
  테스트 참조 갱신.

Ruling R26: String(v) 강제 변환을 Minor 발견으로 취급하지 않고 유지하되 근거를 주석으로 남기게 한다 —
  이 params 는 HTTP 층에서 searchParams.set(k, String(v)) 가 되므로 1 과 '1' 은 바이트 동일한 요청을
  만들고 같은 캐시 항목을 공유해야 옳다. 다만 그 근거가 적히지 않으면 다음 사람이 결함으로 보고 고친다 —
  틀렸을 때 비용: 없음. 주석 한 줄.

Ruling R27: 자진 신고된 세 커버리지 공백을 수용하지 않고 리뷰어에게 등급을 매기게 한다 —
  정직한 공개는 좋은 관행이지만 그 자체로 미검증 실패 경로를 허용하지 않는다. 게다가 이 셋은
  네트워크 클라이언트에서 실전에 가장 많이 실행되고 테스트로는 가장 적게 실행되는 경로이며,
  기존 stub-fetch 하네스로 값싸게 덮을 수 있다 — 틀렸을 때 비용: 리뷰어가 Minor 로 판정하면
  이연 목록에 들어간다. 내가 미리 등급을 정하는 것보다 낫다(pre-judging 금지).

Ruling R28: "정확하지만 미검증" 을 수정 라운드로 처리한다 — 리뷰어가 결함이 없음을 증명했으므로 고칠
  버그는 없지만, 출하 스위트가 그 동작을 붙들지 않으면 지연된 결함이다. 재시도 루프를 다음에 손보는 사람이
  녹색 스위트를 보면서 서버의 Retry-After 지시를 조용히 버리거나, 교차 프로세스 429 경고를 잃거나,
  네트워크 타임아웃을 미처리 rejection 으로 바꿀 수 있다. 이 경로들은 실전에서 가장 많이, 테스트에서 가장
  적게 실행되는 조합이다 — 틀렸을 때 비용: 테스트 5개. 리뷰어가 이미 프로브로 방법까지 보여줬다.

Ruling R29: 내 사전 충돌 스캔이 Task 8 을 "자체 정합" 으로 판정한 것은 오판이었다 — 표를 파생시키는
  코드를 실제로 따라가지 않고 형태만 봤다. 스캔의 B 섹션은 "테스트가 명시하는 것 ↔ 구현이 하는 것" 을
  대조해야 하는데 파생 로직을 통과시켰다. 이후 태스크에서 파생·역전·일괄 변환이 나오면 값을 손으로
  추적한다 — 이 항목은 원장에 남겨 최종 리뷰가 스캔의 신뢰도를 감안하게 한다.

Ruling R30: 원 리뷰의 Important 4건 중 하나(`slot.lockTimedOut` → warnings[])를 내가 수정 지시를
  구성하면서 빠뜨렸다. 결정이 아니라 누락이다 — 구현자의 보고서가 여전히 열린 것으로 표시해 발견했다.
  라운드 2 로 처리한다. 그 경고는 요청률 조율이 실패했음을 호출자가 알 수 있는 유일한 통로다:
  락 조율이 깨지면 이 프로세스는 다른 ctreg 프로세스와 협조하지 않고 추측으로 진행하는데, 추측하면서
  조용히 성공하는 것이 온디스크 버킷이 막으려는 바로 그것이다 — 틀렸을 때 비용: 테스트 하나.
  교훈: 발견 목록을 재구성할 때 항목 수를 대조해야 한다(4건 → 5개 테스트로 재편하면서 하나가 사라졌다).

Ruling R31: 이 Minor 3건을 수정 라운드로 승격하지 않는다 — R23 에서 CAPS 를 승격한 기준은 "소비 태스크가
  CAPS 자체에 대해 단언하므로 틀린 값이 동어반복으로 확인되어 결함이 보이지 않는다" 였다. 여기서는
  리뷰어가 실행으로 전수 확인했으므로 보이지 않는 것이 없고, 다만 고정되지 않았을 뿐이다.
  모든 Minor 를 승격하면 등급 자체가 무의미해진다 — 틀렸을 때 비용: 최종 리뷰가 이 셋을 머지 전
  보강 대상으로 판정할 수 있다. 원장에 남겨 그 판단을 가능하게 했다.

Ruling R32: Task 10 을 Task 9 와 병렬로 dispatch 한다 — 둘 다 src/adapters/ctgov/ 안이지만 파일이
  겹치지 않고(query.ts vs map.ts), Task 10 은 실제 CT.gov 에서 픽스처를 받아오는 느린 단계를 포함해
  가릴 값이 있다. 공유 자원은 .git/index 뿐이고 재시도 지시로 덮인다 — 틀렸을 때 비용: 커밋 재시도 한 번.

Ruling R33(예정, 리뷰 후 적용): --near 단독 시 50km 기본값에 경고를 붙인다 — 이 프로젝트는 단위 없는
  --radius 를 거부하고(추측이 조용히 오도하므로) 날짜 필터가 보이지 않게 좁힐 때 경고를 낸다.
  묵시적 좁힘에는 반드시 경고를 붙인다는 규칙에 반경 기본값만 예외일 이유가 없다. 리뷰어 판정을 받은 뒤
  수정 라운드에 포함한다 — 틀렸을 때 비용: 경고 하나와 테스트 하나.

Ruling R34: 참조 구현에 맞춘다(단일이면 맨몸) — 라이브 필드 테스트로 미루는 대안을 고려했으나,
  참조는 같은 API 에 대해 실제로 동작하는 프로덕션 구현이고 그것에 맞추면 변수를 하나 없애는 반면
  미루면 하나 남긴다. 계획의 테스트는 관찰이 아니라 내 창작이므로 증거로 취급하지 않는다 —
  틀렸을 때 비용: 테스트 2개 수정. 스펙 §7.4 의 필드 테스트 게이트 항목은 그대로 남는다.

Ruling R35 (= R33 확정): --near 단독의 50km 기본값에 경고를 붙인다. 리뷰어가 독립적으로 같은 결론에
  도달했다 — 호출자는 "이 지점 근처" 를 요청했는데 "이 지점 50km 이내" 를 받고, 무엇을 받았는지
  알 방법이 없다. 이 CLI 의 모든 묵시적 좁힘은 경고를 동반한다.

Ruling R36: 커밋 지시를 강화한다 — "경로로 스테이징" 만으로는 부족하다. 인덱스가 한 워킹 트리에서
  모든 에이전트에게 공유되므로, 내 파일만 add 해도 *다른* 에이전트가 스테이징한 파일이 내 커밋에
  올라탄다. 앞으로 모든 dispatch 는 **commit 에 pathspec 을 붙이라**고 지시한다
  (`git commit -m "..." -- <paths>`). pathspec 이 붙으면 누가 스테이징했든 인덱스의 나머지를 무시한다.
  커밋 후 `git show --stat HEAD` 로 파일 목록이 정확히 자기 것인지 확인시킨다 —
  틀렸을 때 비용: 없음. R5/R10 이 예상한 위험은 index.lock 경쟁이었는데 실제로는 다른 형태로 왔다.

Ruling R37: overallOfficials 를 매퍼에 추가하지 않고 요청 목록에서 제거한다 — 그 필드는 PI·연구책임자로
  실제로 유용하지만 centralContacts(등록을 문의할 상대)와 목적이 다르다. 레코드에 넣으려면 두 종류의
  연락처에 걸쳐 `role` 이 무엇을 뜻하는지 정해야 하고 그건 스펙 질문이며, 이미 리뷰를 통과한 태스크를
  건드리는 일이다. 나중 슬라이스가 소비하기를 바라며 지금 필드를 요청하는 것이 leaf 경로 선택이
  막으려던 페이로드 비대 그 자체다 — 틀렸을 때 비용: 슬라이스 2 가 조사자 정보를 원하면 leaf 와
  그것을 읽는 매퍼를 함께 추가한다. 그게 옳은 순서다.

Ruling R38: Task 10 구현자에게 src/core/record.ts(완료된 Task 4 의 파일)와 스펙 §2.2 수정을 인가한다 —
  네 가지로 한정: outcomesTotal 추가(§5.2 가 요구하는 in-record 절단 신호가 스키마에 자리가 없었다),
  crossIds[].registry 를 optional 로, crossIds[].domain 추가, eligibility.sexRaw 추가.
  전부 발견이 요구하는 것이고 대안이 없다 — outcomesTotal 없이는 스펙 §5.2 를 만족할 수 없고,
  registry 를 필수로 두면 C1 을 고칠 수 없다 — 틀렸을 때 비용: Task 4 의 테스트가 깨지면 즉시 드러난다.

Ruling R39: crossIds 의 의미를 스펙에서 정정한다("타 레지스트리 중복 등록" → "부차 식별자, registry 는
  업스트림 라벨") — 필드가 과잉 주장하고 있었고 그것이 I7 을 그럴듯해 보이게 만들었다. 페더레이션을

Ruling R40: Task 12 를 Task 10·11 수정 라운드와 병렬로 dispatch 한다 — Task 12 는 map/results/client 의
  함수를 import 만 하고 편집하지 않으며, 진행 중인 수정은 시그니처가 아니라 내부와 스키마 필드 추가다.
  새로 만드는 파일(adapter.ts, adapters/index.ts)도 겹치지 않는다 — 틀렸을 때 비용: 픽스처 기반 단언이
  map 수정으로 흔들릴 수 있어, dispatch 에서 stub 을 쓰고 레코드 깊은 값에 단언하지 말라고 지시한다
  (그건 Task 10 의 몫이다).

Ruling R41: ndjson 에 후행 메타데이터 줄을 도입한다 — data 행 뒤에 항상 한 줄,
  {"_meta":true, query, registries, warnings, error}. **항상** 낸다(있을 때만 내면 소비자가 매 줄마다
  검사해야 하고 결국 틀린다). 대안 셋을 기각했다: (a) 경고를 stderr 로 JSON — "stdout 은 기계용,
  stderr 는 사람용" 이라는 이 프로젝트의 규칙과 모순되고 스킬이 사실 하나를 알려고 두 스트림을 파싱해야 한다.
  (b) 선행 메타 줄 — 같은 판별자가 필요한데 스트리밍 소비자가 즉시 레코드 처리를 시작하지 못하게 막는다.
  그게 ndjson 이 존재하는 유일한 이유다. (c) 모든 행을 봉투로 감싸기 — 줄=레코드 성질을 파괴한다.
  `_meta` 가 안전한 판별자인 이유: 이 CLI 가 내는 어떤 레코드의 필드도 아니고 스키마가 strict 라
  우연히 획득될 수 없다 — 틀렸을 때 비용: 스펙 §5.1 한 문단과 테스트 3개. 형식이 조용히 거짓말하는
  것보다 낫다.
  리뷰어가 error+unsupported 혼합 시 exit 4 에 대한 내 논리를 독립 검증하고 동의했다(내 요청대로
  받아들이지 않고 검증했다). 다만 "동의는 테스트가 아니다" 로 고정을 요구했다 — 옳다.

Ruling R42: R36 의 커밋 지시를 정정한다 — `git commit -- <경로>` 는 **이미 추적되거나 스테이징된**
  경로만 제한하며, 미추적 새 파일을 자동으로 추가하지 않는다("did not match any file(s) known to git").
  새 파일을 만드는 태스크는 `git add <경로>` 를 먼저 하고 그 다음 `git commit -- <같은 경로>` 를 해야 한다.
  두 단계 모두 필요하다: add 가 파일을 인덱스에 넣고, commit 의 pathspec 이 다른 에이전트가 스테이징한
  것을 배제한다 — 틀렸을 때 비용: 없음. 구현자가 실제로 부딪혀 보고했다.

Ruling R43: ⚠️ 를 "구조적으로 동일한 경우가 고정돼 있으니 괜찮다" 로 넘기지 않고 수정 라운드에 넣는다 —
  그 추론("작동하는 것과 구조적으로 동일하다")이 이 프로젝트에서 이미 두 번 틀렸다(Task 4 의 strict 중첩,
  Task 5 의 락 밖 쓰기 — 둘 다 형제 코드는 맞았는데 해당 경로만 틀렸다) — 틀렸을 때 비용: 테스트 하나.
